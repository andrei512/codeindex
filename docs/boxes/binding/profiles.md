# Language binding profiles

A profile defines which evidence a language pack supplies, which contextual lookup consumes it, and which identities and public answers must survive a native rewrite. The archive's language registry has 17 modes. Markdown navigation also handles document addresses. These are design and conformance requirements; a named oracle identifies a comparison target, not a shipped dependency or a claim of verified coverage.

## Identity rules shared by the profiles

Within an analysis, a written declaration or use has a typed local ordinal and a source span. Binding gives the site a role and target in a file and context. Merged declarations can contribute several sites for one symbol. Two overloaded methods can have identical spellings and distinct targets. Intern the language key once per retained namespace. Store target ordinals in bindings. Order of worker completion must never allocate a public label.

When a language introduces an entity without a separately written declaration, use a generated key with the producing semantic namespace, owning symbol or expansion site, generated role, and a deterministic discriminator supplied by the pack. Multiple outputs of the same macro invocation require distinct discriminators. Preserve the mapping to a source site when the reference oracle exposes one. An implicit symbol can have no user-visible declaration span. Derive exported keys from the language's actual package instance and descriptor. A spelling or byte offset in isolation is insufficient.

For compatibility, a public label can be a projection of a native identity. Preserve the archived logical label when comparing frozen graph rows and public output. Two key encoders are relevant:

- **SCIP-derived rows.** The archived importer prefixes a document-local descriptor such as `local 4` with engine name and repository-relative document path. For a non-local descriptor it prefixes engine name and export base relative to the repository. Each prefix component is separated by one space; an empty base still occupies its place. Preserve the exporter’s descriptor bytes, including escaped identifiers, numbering, package version, and method or type disambiguators. One symbol can retain a compact descriptor recipe or an interned label once. Local numbering is independent of file-worker completion. An internal declaration ordinal need not equal the exported local ordinal.
- **Server-derived rows.** A recognized declaration uses the engine name, repository-relative target path, decimal start byte, and original spelling separated by spaces. A definition found only through navigation uses the same prefix through the start byte and has no spelling suffix. A reference binds to that target identity. The compiler-backed and navigation-backed profiles may name the same source differently. Preserve the identity of the path actually used for the frozen comparison.

The archive converts positive-length source ranges to canonical bytes, records definition roles, and derives calls by matching a non-definition occurrence to the syntactic call-target range. It resolves the optional enclosing caller from the declaration at the enclosing introduction site. Keep ownerless calls. Conformance compares file coverage, definition spans and identities, non-definition spans and identities, target and optional caller, coordinate conversion and distinct query results. A generated target with an unprojectable source range can still be a reference target. Never invent a navigable declaration location.

## Code and schema profiles

The evidence column names data a pack must make available when the indicated construct occurs. Persist the minimum needed for rebind after a dependency change. Each fixture exercises an identity collision or a coverage boundary. Where the old provider gives several targets, preserve its observable target set and separately record the evidence available for certainty.

## Context configuration inputs

Use these public configuration map names where an input affects a profile: `package` for the package or assembly instance, `language_version` for edition or dialect, `scope` for a named project subunit, `features` and `defines` for effective conditional settings, `imports` for ordered resolution roots or aliases, `dependencies` for logical package and SDK identities, and `options` for remaining typed lookup-affecting settings keyed by canonical language option name. Lists of search roots preserve precedence. Feature sets and unordered package maps have canonical order. Omit a setting that has no meaning for the pack. Include the normalized effective value, including defaults, for every setting the pack uses. Use boolean, integer, string, null, list and map values under the [context key encoding](../../domain.md#public-context-keys-and-coverage-reasons).

For Rust, project identity and scope distinguish the manifest path and crate target, including a library and a binary in the same package; features and target cfg affect lookup. For JS/TS use the chosen tsconfig or synthetic project identity, effective module mode, path aliases, type roots and declaration dependencies. Python uses the analysis entry, Python version, import roots and environment identity. C# uses project, assembly, framework target and conditional defines; C/C++ uses translation-unit project identity, include path order, preprocessor settings and target. Swift uses module, SDK and active conditions. Shell and PowerShell use the script/module context and ordered search roots consulted. Proto uses import roots and package context; HTML and CSS use the source and embedded dialect where applicable. A configuration whose external provenance cannot be verified gets incomplete coverage. Do not assign two observably different contexts one public key by dropping the unknown input.

## Conformance and provenance

For every supported binding path, freeze a fixture's source, effective context, public selectors, identities, source spans, roles, caller owners and capability statuses. Add conflicting names and a change that must remove or retarget one edge. Compare the whole projection after a fresh build, a reopened build and the edit. An archived name-extraction fixture alone establishes syntax coverage. Mark a semantic path verified only after its semantic fixture passes. If a successful frozen answer depends on unavailable generated evidence, that answer remains a parity obligation until the native pack can reproduce it.
