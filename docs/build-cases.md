# Build and query cases

A query must give the same observable answer whether its generation was built from an empty store or refreshed from a predecessor. The cost depends on which inputs changed. These cases specify both the answer and the work an implementation must account for.

| Input or event | Work and sharing | Assertion at the CLI or store boundary |
| --- | --- | --- |
| Empty store, stable checkout | One elected builder inventories the tree. Capture each required version. Share its source across lexical consumers and distinct syntax modes. Route local facts while other files are being read. Close dependency scopes before finalizing affected bindings. Seal each required product, including empty ones. | Reopen in another process. Every query family succeeds against the published generation. A simultaneous cold caller causes zero extractions of its own. |
| Fresh generation, unchanged checkout | Validate membership, file versions, control files, project inputs and rules against the selected generation. Borrow its handles for the query. | Same generation. Zero new source captures, extractions, binding partitions, posting writes and publication syncs. On a filesystem that requires content validation, account for those validation reads separately. |
| Edit one file | Capture the changed version, replace its affected facts, requalify postings and adjust visible corpus statistics. Independent files keep their sources and analyses. Propagate changed binding inputs through their recorded dependents. | A unique removed term disappears and a new one appears. BM25 on an untouched chunk reflects the new corpus. A relationship lookup through an unchanged caller matches a fresh build. |
| Rename, delete, or change eligibility | With verified source identity and mode, reuse local facts. Replace path fields, relative targets, context membership and affected bindings. Retire deleted file contributions and update corpus counts. A simultaneous delete and unrelated create may require capture. | Old path disappears. A moved link resolves against its new parent. A reader already holding the previous pin still reads the old section and path. An ignore-only edit can add or remove an untracked path. |
| Dependency or config change | Compare the projections used in binding. Reuse parsing where the syntax mode survives. Re-evaluate affected resolution, including prior misses. Different syntax-affecting options select a separate analysis. | A newly introduced shadowing declaration changes the target. Removing the declaration restores it. When the retained export projection is proven equal, its revision stays stable and consumers of just that projection keep their bindings. Report conservative invalidations separately. |
| Concurrent refresh and query | Elect one writer. Keep metadata locking short. The reader holds immutable handles through traversal and formatting. If validation raced a generation switch, retry the selection. | Pause a reader after it acquires its pin. Publish and reclaim unreachable names. Resume the reader. Every offset, score, breadcrumb and source byte belongs to its original generation. In a second run pause before pin upgrade, switch the selected generation, and require a fresh validation before the caller can use the new pin. Use disjoint hit text in the two generations. |
| One worker, constrained memory, one frequent term | Admit the next bounded unit with its credits. Suspend at an owned cursor. Allow the drain step to spill an open partition before the last producer closes. | Under a budget sufficient for the minimum supported working set, finish with the same results as an unconstrained build and no replayed parser prefix. Inject a spill error with the producer suspended. All charges and promises must unwind exactly once; retry under the same budget. Below the minimum return a resource error and preserve the previous generation. |
| Crash or failed write | Inject failure after each private write, segment sync, segment installation, selector replacement and directory sync. Keep the predecessor reachable through uncertain publication. | Reopen to one complete permitted generation, or rebuild if the first publication never completed. No reader sees a mixture. A retry succeeds after the fault is removed. |

A fresh checkout comparison checks results, including ordering, coverage, scores, contexts and display ranges. Generation IDs, elapsed times, cache paths and allocation ordinals can differ. Counter assertions also matter. An implementation that reparses the repository after every edit can pass every result comparison in this table.

## Observing work

In a diagnostic build, record a count and logical byte total at each transfer of ownership. Key source captures by observed object and version, extractions by source and mode, bindings by partition and consumed revisions, and product memberships by their actual uniqueness key. Separate rereading a private posting run from rereading a source file. Split invalidated attempts from successful work. Count reserved capacity, resident buffers, mapped windows and private spill bytes separately. Sample process resident memory and OS I/O alongside these measures. Logical bytes alone cannot establish bandwidth use.

Run the same change sequence serially, with multiple workers, and with forced suspension. Vary enumeration and completion order. Compare visible answers after each transition with an independent empty-store build of the same inputs. For publication, hold an old pin across each transition and check its answers too. The component references define the fixtures that exercise each boundary.
